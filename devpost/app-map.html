One tap, followed through the code

The route (3 stops)

1The tap is caught — app.js, search btn.dataset.color and function choose.
Every colour button carries a label like data-color="YELLOW". One listener passes that label to choose(), which saves it under the patient's id in state.answers. Then it shows the next card, or calls endRound() after card 15.

Show the code 
btn.addEventListener("click", () => choose(btn.dataset.color))

function choose(color) {
  const c = state.order[state.index];
  state.answers[c.id] = color;
  state.index++;
  if (state.index < state.order.length) renderCard();
  else endRound();
}

2The algorithm decides — start.js, search function startTriage.
This is the START algorithm written as one function. It checks walking → breathing → respiratory rate → perfusion → mental status in order and returns at the first step that decides. The answer key is never typed by hand: scoreRound() in app.js asks this function for the right answer, then classifyError() labels your choice correct, over- or under-triage.

Show the code 
if (p.rr !== null && p.rr > 30) {
  return { color: "RED", step: "respiratory rate",

}

3You see the explanation — app.js, search function renderReview; sentence built by explain() in start.js.
For each wrong or untriaged patient it builds one review card: narrative, your choice, correct colour, deciding step, and the sentence that slots the algorithm's reason into "You chose {choice}, but {reason} means {colour} at the {step} step."

A practice to reuse

Make the computer check the expert content. The brief listed the expected colour for each of the 15 cases. Instead of trusting them, selfcheck.js runs every case through startTriage() and compares the results (all 15 PASS, mix 3/5/5/2). That check was the first build step, before any screen existed, so every later step rested on a verified answer key.

The same approach works on other projects: whenever an app depends on rules (a scoring system, a clinical guideline, a protocol), write the rule as one small pure function. Then write down a handful of known cases with their expected answers, and check them automatically before building screens. It works like validating an instrument before a study.
